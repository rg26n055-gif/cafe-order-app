# CAFE ORDER — カフェの注文・会計・厨房・在庫管理

**受付から商品のお渡しまでを、ひとつの画面で管理するスタッフ向けWebアプリです。**

- **公開アプリ：[CAFE ORDERを開く](https://cafe-order-rg26n055.iisiu.chatgpt.site/)**
- **ソースコード：[GitHub / cafe-order-app](https://github.com/rg26n055-gif/cafe-order-app)**

Googleアカウントでログインして使います。ChatGPTのアカウントは不要です。アカウントごとに注文・在庫が分かれ、新しくログインした人は自分専用のデータで始められます。初期在庫は0なので、最初に「在庫」で販売可能数を設定してください。

## どんな課題を解決するか

カフェの運営では、受付・会計・厨房の間で「何を注文されたか」「会計が終わったか」「商品がそろったか」を共有する必要があります。別々の画面や記録で管理すると、確認の手間や伝達漏れが生じやすくなります。

このアプリは、元のGoogle Apps Script・スプレッドシート版の業務の流れをもとに、注文・会計状態・調理状況・在庫をデータベースで管理する構成へ作り直したものです。Google Sheetsへの接続や、スプレッドシートの準備は不要です。

## このアプリのポイント

- **5つの業務を集約**：注文受付、会計、厨房、綿あめフロート、在庫をタブで切り替えます。
- **Googleログインとデータ分離**：Aさん・Bさん・Cさんはそれぞれ独立した注文・在庫を使います。同じアカウントで別端末から開くと同じデータを参照できます。
- **注文時に在庫を確保**：複数の注文が重なっても、在庫を超える注文を保存しない設計です。
- **二重処理への対策**：同じ注文の再送や取消の重複でも、在庫を二重に増減させないようにしています。
- **状態を残す運用**：会計・調理・提供の順に進み、提供済みの注文も記録を残します。

別のGoogleアカウント同士で同じ店舗を共同管理する招待機能は、現在未実装です。アカウントごとの独立したワークスペースとして利用します。

## 操作の流れ

1. **在庫**：販売開始前に、各商品の販売可能数を設定します。初期在庫はすべて0です。
2. **注文受付**：店内／テイクアウト、お客様番号、チケット種別、商品と数量を選んで登録します。この時点で在庫を確保します。
3. **会計**：代金・チケットを受け取ったら「会計済みにする」を押します。会計済みの注文が厨房に表示されます。
4. **厨房／綿あめ**：担当ごとに「調理完了」を記録します。
5. **厨房**：すべての商品がそろったら、お客様へ渡して「提供済みにする」を押します。

会計状態の記録のみを行います。オンライン決済、送金、返金、領収書発行は実装していません。

## 商品と受付条件

- ドーナツ・カップケーキ・チュロス：各250円
- 綿あめフロート：200円／パック：50円
- 店内のお客様番号は1〜40、テイクアウトは1〜8。
- チケット種別は「前売り券」「当日券」。種別による価格差はありません。
- 商品ごとの数量は1〜10個。在庫数を超える注文はできません。
- テイクアウトにはパックが1個以上必要。パック売り切れ時は受付できません。
- 店内飲食ではパックを選べません。パックだけの注文も登録できません。

商品名・初期価格は `lib/catalog.ts` に定義しています。登録済みの商品情報はデータベース側に保存されるため、コードの初期値だけを変えても既存の商品情報は上書きされません。

## 5つの業務画面

- **注文受付**：商品選択、数量調整、合計金額表示、注文登録
- **会計**：未会計、会計済み、提供済み、取消済みの切り替えと会計記録
- **厨房**：会計済み注文を受付順に表示、厨房の調理完了、全品の提供完了
- **綿あめ**：未調理の綿あめ注文、お客様番号、数量、前後への移動
- **在庫**：現在の販売可能数の確認と変更

画面は10秒ごとにデータを再取得します。更新ボタンでも再取得できます。当日の基準時刻は日本時間です。画面の履歴は進行中の注文と当日の注文・会計分に限定しますが、過去の記録もデータベースに残ります。

## データの一貫性

- 注文ヘッダー・明細の保存と在庫減算を、D1の同じトランザクションで実行します。
- 在庫の非負制約により、残り1個に複数注文が同時に入った場合、確保できなかった注文全体をロールバックします。
- 金額はサーバーの価格から計算し、注文時の単価を明細に保存します。ブラウザーから送られた金額を信用しません。
- 同じ注文IDの再送では、注文と在庫を二重登録しません。送信結果が不明な場合のID・下書きはタブ内のセッションストレージに一時保存します。正式なデータはデータベースに保存します。
- 未会計の注文のみ取り消せます。取消と在庫戻しは一括処理し、重複操作でも二重に在庫を戻しません。
- 会計済み注文の取消・返金は未対応です。
- 在庫変更時は編集開始時の在庫と照合します。他端末の注文で在庫が変わった場合、上書きせず再確認を求めます。
- 提供済みの注文は削除せず、状態と時刻を記録します。

## 公開コードと運用画面

GitHubのソースコードは公開です。実際の注文・在庫データ、元のスプレッドシートID、認証情報は含めません。

入口は誰でも開けますが、注文・在庫の取得や更新にはGoogleログインが必要です。Firebase Authenticationで認証し、サーバーでは署名・発行元・対象プロジェクト・有効期限・Googleプロバイダ・確認済みメールを検証します。ChatGPTのアカウントは不要です。

Googleアカウントごとに独立したワークスペースを持ちます。同じGoogleアカウントなら別端末でも同じデータ、別アカウントなら別データです。商品・注文・明細・取消操作にはすべて所有者のUIDが付き、複合キーとサーバー側の条件で分離します。リクエストに別人のUIDを付けても切り替えられません。新規アカウントの在庫は0です。

これは個人ごとのワークスペースです。別アカウントのスタッフ同士で同じ店舗を共同管理する招待・権限機能は未実装です。パスワードを共有して運用しないでください。

ブラウザーのログイン状態はタブのセッションに保存します。ログアウトすると業務画面を破棄し、別の利用者の画面に引き継ぎません。送信結果が不明な注文の下書きもUIDごとに分離しています。Firebaseでのアカウント停止やトークン失効は既発行IDトークンの期限切れまで（通常最大1時間）即時反映されません。

旧版のデータは元のテーブルに残します。非公開の環境変数 `LEGACY_OWNER_EMAIL` に指定した確認済みGoogleメールの利用者に限り、初回読み込み時に一括コピーします。移行は一度だけ・トランザクション内で実行し、新規利用者には旧データを渡しません。メールの設定は既存データ所有者のGoogleアカウントを確認してから行ってください。

## 技術構成

- React / TypeScript：画面と入力処理
- Vinext / Vite：開発・ビルド
- Cloudflare Workers：API処理
- Cloudflare D1（SQLite）：商品・注文・明細・操作の保存
- Drizzle：スキーマ定義とマイグレーション
- Firebase Authentication：Googleログイン
- Sites：ホスティング・データベースの公開環境

GitHub Pagesだけではサーバーとデータベースが動かないため、そのままGitHub Pagesへ配置することはできません。

## ローカルで動かす

Node.js 24以上とnpmを用意し、このフォルダで実行します。

```sh
npm ci
npm run build
npm run db:local
npm run dev
```

`db:local` は未適用のマイグレーションだけを実行します。旧版のローカルDBにも対応しています。スキーマ変更後は再実行してください。

`http://localhost:5173/` を開き、Googleでログインしてください。ローカルでも実際のFirebase認証を使いますが、注文・在庫の保存先はローカルDBです。Firebase Authenticationの承認済みドメインに `localhost` と本番のドメインを登録します。Webアプリの公開設定値は `lib/firebase-config.ts` にあります。秘密鍵・サービスアカウント鍵は不要です。

ローカルデータは `.wrangler/` に保存されます。GitHubにはコミットせず、本番データへの自動移行も行いません。

## 検証

```sh
npm test
npm run typecheck
npm run build
```

既存の注文処理に加え、利用者間の分離・旧データ移行・認証トークン検証を自動テストしています。

- 注文による在庫確保・サーバー単価・同じ注文の再送
- 不正数量、未登録商品、同一商品の重複を拒否
- パックと店内／テイクアウトの受付条件
- 同時注文による在庫不足と注文全体のロールバック
- 同一注文の同時再送
- 会計・各担当の調理完了・提供の順序
- 同時取消で在庫が二重に戻らないこと
- 会計と取消の競合時に状態と在庫が一致すること
- 会計済み取消の拒否と古い在庫値での上書き拒否

- A/B/Cの在庫・注文の分離、別人の注文操作の拒否、同一IDでの独立動作
- 一覧読取の所有者条件と新規アカウントの在庫初期化
- 旧データ移行の所有者制限・同時実行・元データの保存
- 署名偽装・別プロジェクト・期限切れ・未確認メール・Google以外のログイン拒否

注文・在庫の業務フローはローカルのテストデータでブラウザー確認を行っています。Googleログインへの変更後、本番で実際のGoogleアカウントを使ったログインから注文・提供までの一連の確認は未完了です。自動テストによる検証と、本番端末での動作確認は区別しています。

## 制限

- インターネット接続が必要。オフライン注文には未対応です。
- 同じお客様番号で複数注文を登録できます。注文IDと受付時刻を合わせて確認してください。
- 登録済み注文の内容変更、会計済み取消、返金、CSV出力は未対応です。
- リアルタイム配信ではなく10秒ごとの更新です。
- 大人数・大量注文での負荷検証は行っていません。
- 元のスプレッドシートのデータは移行していません。

## 開発の進め方とAIの利用

元のApps Script版の業務の流れと価格・受付条件をもとに、スプレッドシートを使わないアプリへの移行、Googleログイン、アカウントごとのデータ分離を要件として進めました。コードの実装・テスト・ドキュメント作成には、AI開発支援ツールのCodexを使用しています。

本リポジトリは、すべてのコードを手作業で書いたことや、記載した技術をすべて習得済みであることを示すものではありません。要件の整理とAIを使った開発の成果として公開し、実装を読みながら理解を深めるためにも活用します。
